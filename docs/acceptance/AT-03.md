# `AT-03`: `"backfill"` Mode on `RTSP`-Capable Cameras - Human Frigate Live View vs. `/api/wake`

- On an `RTSP`-capable camera configured with `mode: "backfill"`:
  1. Startup property sync must enable `rtspStream: true` so `rtspStreamUrl` is ready for on-demand viewing.
  2. Opening a single-camera Live View in Frigate (`pollViewers`) while `IDLE` with **no** pending `BackfillJob`
     **must** wake a live **`RTSP`** session (`STREAM_MODES.RTSP`), never `P2P`. While a `BackfillJob` is pending
     (`hasPendingBackfill()`), `pollViewers` **must block** the Live View wake (`ignored, waiting for HomeBase clip
backfill`) and keep the **Yellow** (`Waiting` / `busy`) status card visible so the `BackfillJob` is not
     interrupted or canceled.
  3. Calling `POST /api/wake/:cameras` while `IDLE` with **no** active Eufy hardware trigger or pending `BackfillJob`
     **must** wake a live **`RTSP`** session (`status: "waking"` / `"scheduled"`) and file a Frigate event (unless
     `create_event: false`). Calling `POST /api/wake/:cameras` when a Eufy hardware trigger, pending `BackfillJob`, or
     active backfill playback (`isBackfillPlayback()`) is already in progress **must** stay in backfill mode and
     upgrade/extend the `BackfillJob` (`status: "backfill"`), whereas calling it while already streaming live extends
     the active live hold (`status: "extended"`).
