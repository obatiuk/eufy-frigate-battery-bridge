# `AT-08`: Post-Sleep `3s` Guard, Idle Wedged `P2P` Radio Recovery & Service Disruption Resilience

- Across all camera modes:
  1. For `3 seconds` after a session ends (and while `device.stop_livestream` is still in flight), trailing
     `'livestream video data'`, `'livestream started'`, or `'rtsp livestream started'` messages must be ignored so a
     closing session never re-wakes itself.
  2. Unsolicited `'livestream video data'` arriving while `IDLE` must never self-adopt as a live wake; past the `3s`
     post-sleep guard, it must send `device.stop_livestream`.
  3. If an `IDLE` camera's radio remains wedged (`>= 4` `wifiRssi` changes within `60s` at least `15s` after a completed
     session), the bridge must send only `device.stop_livestream` - never `station.disconnect` or
     `device.cancel_download`.
  4. When `eufy-security-ws` disconnects mid-session (`ws_closed`), active sessions must terminate immediately and
     return cameras to `IDLE` (`error/ws-disconnect`) so no camera remains stuck in `WAKING_*` or
     `STREAMING_LIVE`, while `/healthz` keeps returning `200 OK` (`{"ok": true}`, with no `ws_connected` or other
     external service fields) so container health checks reflect only bridge process liveness (`503` `{"ok": false}`
     only on shutdown) and never restart the container during external service outages while the bridge logs the outage
     and reconnects automatically. When `Frigate` (`frigate_url`) or `go2rtc` (`go2rtc_url`) is temporarily unreachable
     or restarts, live streaming and `.zxvideo` backfill must continue uninterrupted with scoped outage and recovery log
     messages; once `Frigate` recovers, the bridge must automatically re-sync `eufy_bridge_card` masks and re-seed
     offline snapshots (`seedOfflineCameraSnapshots`).
