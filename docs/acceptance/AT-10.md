# `AT-10`: Non-Invasive `power_mode` & `streaming_quality` Profiles, Metadata Sync & Stuck Spotlight (`light`)

- Hardware Power Manager, `streaming_quality` profiles, and experimental stuck-spotlight (`light`) conservation:
  1. Both `power_mode` and `streaming_quality` must default to `"keep"` (sending zero Power Manager or
     `videoStreamingQuality` `device.set_property` writes on startup and dynamically mirroring omitted `hold_secs` /
     `end_early` from reported Eufy telemetry: `0 -> 20s`, `1 -> 60s`, `2 -> recordingClipLength /
recordingEndClipMotionStops`, with `30s` live / `20s` backfill and `end_early: true` fallbacks before telemetry), and
     the bridge must inspect reported Eufy Motion Detection settings (`motionDetection`, `motionDetectionTypeHuman`,
     `motionDetectionTypeHumanRecognition`, `motionDetectionTypeVehicle`, `motionDetectionTypePet`,
     `motionDetectionTypeAllOtherMotions`, `loiteringDetection`, `soundDetection`) strictly read-only (never writing
     them) to emit a deduplicated `WARN` log whenever `motionDetection` is `false` or active `trigger_events` include
     detection categories disabled in the Eufy app (emitting no warning when `trigger_events` matches the camera's
     enabled detection types).
  2. When opted in, all `device.set_property` commands for a camera must execute sequentially (never concurrently in
     parallel), and whenever configured `power_mode` or `streaming_quality` settings differ from the camera's reported
     existing settings, the bridge must emit a `[WARN ]` log printing the camera's existing settings alongside the
     target override values (emitting no override warning when `"keep"` is active or existing settings already match):
     `power_mode: "battery"` syncs `powerWorkingMode = 0` (`20s` hold), `"surveillance"` syncs `powerWorkingMode = 1`
     (`60s` hold), `"custom"` (in camera `mode: "custom"`) syncs `powerWorkingMode = 2` plus `recordingClipLength`,
     `recordingEndClipMotionStops`, and `recordingRetriggerInterval` (`5s` default), and `streaming_quality` (`"auto"`,
     `"low"`, `"medium"`, `"high"`, `"ultra"`, or `0..10` in `mode: "custom"`) resolves device-specific tier codes via
     `device.get_properties_metadata` (`states`) while latching permanent `device_invalid_property` /
     `device_invalid_property_value` / `device_not_supported` rejections without `5`-minute retry loops.
  3. The bridge must never turn on or toggle the camera's built-in spotlight (`light`) during normal session start/stop
     or at startup. Experimental stuck-spotlight tracking (`track_stuck_spotlight`) must default to `false`, leaving
     `light` untouched even if `light: true` stays reported past `130s` while `IDLE`.
  4. Only when `track_stuck_spotlight: true` is configured (globally or per-camera), the bridge turns off a stuck
     spotlight (`light: false`) via the `500ms` housekeeping watchdog (or idle wedged-radio recovery) whenever the
     camera is `IDLE`, has no active hardware triggers (`state: false`), no pending `BackfillJob`, no backfill playback,
     and `light: true` has stayed on for `> 130s` since the later of the light turning on and the last session or motion
     activity; a freshly lit spotlight is never judged stuck (it may be lighting a hardware clip that is still
     recording).
